# Findings, all fixed at the sync commit

The code once wrote `addons/{id}/{version}/` before `decide` committed. A review's `publish` (`publish-version.ts`) now reads and verifies (`readVerified`), commits (`commitReview`'s transaction: `decideSubmission`, `makeLive`), and only then writes (`writeFiles`). The CAS on `status = 'pending_review'` and the `addon_version` primary key decide who wins before any byte is public, so a request that loses writes nothing. `before-fix*` keep the old order; TLC still fails it, and the replays below failed on it.

1. **Approve racing reject or ban left rejected files public** (bundle, manifest, extra files, store page, media). A read the loser had started could still land its writes after the winner committed. Fixed: the loser fails the CAS before writing. Invariants `PublicOnlyIfLiveAtRest`, `RejectedNeverPublic`; replay `approve races reject` holds the approval in its staged read.
2. **A stale approval overwrote a live version's files.** s1's approval was read, s1's author banned, s2 for the same version approved, then s1's writes landed under s2's row. Fixed the same way. Invariant `PublicMatchesLive`; replay `stale approval overwrites a live version`.
3. **Two pending updates for one version** (`SUBMISSION_MAX_PENDING_UPDATES` >= 2): the second approval rewrote the first's live files and then failed on the `addon_version` key. Fixed: `decide` throws first. Replay `second pending update overwrites`.

4. **A public write that fails after `decide` committed left a live version without its files for good** (the cost of the order above). Fixed: any reviewer repeating the approval on the approved submission, while its `addon_version` row still names it and `files_pending_since` is set (`hasPendingFiles`; `makeLive` sets it in `decide`'s transaction, `writeFiles` clears it after the writes with `markFilesPublished`), skips `decide` and runs the same read, verify and `writeFiles`, which overwrites every key with the verified bytes. One nullable column, no new write path: the only review writer is still `writeFiles` after a verified read, for a row `decide` already committed, and a version another submission replaced is refused. Model: `WriteFail` (at most `MaxWriteFailures` per run, partial writes allowed) and `RetryStart`; `current*` keep all six invariants with failures. Liveness `LiveEventuallyPublic` (a live version eventually has all four public file groups) holds in `current-liveness` under fair retries and read, write, decide and cleanup steps (`LiveSpec`); `broken-no-recovery` (`Recovery = FALSE`) violates it. The staff review queue lists an approved submission while the column is set, so a reload still offers the retry. Replay `failed publish recovers`: the first public write fails, the queue (a fresh request) still lists the approval, a rejection is refused, another reviewer's retry publishes every file with the live row's sha256 and takes it off the queue, and a second repeat is refused.

Limits of the recovery proof: `current-liveness` sets `AllowTamper = FALSE`, because a staged object changed outside the app and never replaced fails every re-hash and blocks any approval or retry (`readAtPin` prefers the staged object over the pinned blob); and it needs someone to repeat the request, the fairness assumption, since nothing retries on its own (the queue keeps offering the retry, but a reviewer still has to click). The model drops the `files_pending_since` guard and the sweeper's keep rule, which only narrow `RetryStart` and `Orphan`. `deleteOrphans` keeps the staged bundle of an approved submission only while its version is unpublished; recovery does not need it, as `readAtPin` refetches the pinned blob and `verifyBundle` re-hashes it (`Orphan`, replay `approval refetches a lost bundle`). A repeat with a GitHub outage and a swept bundle fails and can be repeated. The model has no first-party publishing (`replaceLive` included): a repeat that races it is outside the model. First-party writes its files before it commits, so its versions never have `files_pending_since` set and never enter this recovery; a failed first-party write leaves the previously served version served, and repeating the publish writes and commits it (test `tests/lib/publish-version.test.ts`).

`PublicOnlyIfLive` holds too: the files appear only after the row exists. The one window left is a live row whose files are not yet written: until `writeFiles` lands, `findUpdates` and the listings already serve it.
