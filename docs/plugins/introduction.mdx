A plugin is a bundle of JavaScript that Unbound loads, evaluates, and runs inside Discord. Plugins add functionality the base app doesn't ship, using the [Developer API](/modules/introduction): Metro to find Discord's internals, storage for settings, and the [patcher](/modules/patcher) to change behavior.

### The shape of a plugin

A plugin is an object with optional lifecycle hooks. Unbound calls `start` when the plugin is enabled and `stop` when it's disabled.

Set up everything the plugin does (patches, listeners, subscriptions) in `start`, and tear all of it down in `stop`.

```ts
export default {
	start() {
		// set up patches, listeners, subscriptions
	},
	stop() {
		// undo everything start() did
	},
};
```

<Note>
	Whatever you create in `start`, undo in `stop`. A disabled plugin should leave nothing running. Leftover patches and listeners are the most common source of bugs after a plugin is disabled.
</Note>

### How plugins are loaded

**Unbound loads and evaluates every installed plugin's bundle at startup, whether or not the plugin is enabled.** For a disabled plugin, Unbound never calls `start`, but the bundle's top-level code still runs.

This means anything at the top level of your bundle runs for every user on every launch, even when your plugin is turned off.

<Warning>
	Do not run [Metro](/modules/metro) searches at the top level of your plugin. `findByProps`, `findByName`, and the other search functions walk the module registry. Running them at import time, for a plugin that may be disabled, slows down startup for every user.
</Warning>

### Writing a fast plugin

Two techniques keep a plugin's startup cost near zero until it's enabled and used.

<Steps>
	<Step title='Defer module lookups with lazy' icon='clock'>
		Pass the `{ lazy: true }` search option to top-level Metro lookups. The search then runs the first time you *access* the result (inside `start`, or later inside a handler) instead of at import.

		```ts
		import { metro } from '@unbound-app/api';

		// Deferred: resolves on first access, not at import.
		const Messages = metro.findByProps('sendMessage', 'receiveMessage', { lazy: true });
		```
	</Step>
	<Step title='Split heavy work behind a dynamic import' icon='code-branch'>
		Keep your bundle's entry point small. Move code that pulls in many modules into separate files, and `import()` those files inside `start`. That code then loads only when the plugin runs.

		```ts
		export default {
			async start() {
				const { apply } = await import('./patches');
				apply();
			},
		};
		```
	</Step>
</Steps>

<Tip>
	Structure your plugin as a small entry point plus modules it loads on demand. At import time, the entry point should do almost nothing beyond declaring lazy handles and waiting for `start`.
</Tip>
