### What is Settings?

`settings` is a registry of settings screens. Each entry you register becomes a real route in Discord's settings navigation, listed in the Unbound section next to the built-in General, Plugins, Design, and Developer pages.

It registers _screens_, not values. [storage](/modules/storage) persists the values those screens read and write.

```ts
import { settings } from '@unbound-app/api';
// equivalent: import settings from '@unbound-app/api/settings';
// runtime global: unbound.settings
```

<Note>
	Most plugins don't need this module. If a plugin exports `getSettingsPanel`, its card in the Plugins list already gets a settings button, and Unbound renders the returned node on a screen for you. Use `registerSettings` when you want a top-level entry of your own in the settings list, separate from your plugin's card.
</Note>

### Registering a screen

`registerSettings` adds one or more entries to the registry. Entries are keyed: registering the same key again overwrites the previous entry and logs a warning.

```tsx
import { settings } from '@unbound-app/api';

import MyScreen from './my-screen';

settings.registerSettings({
	type: 'route',
	key: 'MY_PLUGIN_SETTINGS',
	useTitle: () => 'My Plugin',
	parent: null,
	section: 'Unbound',
	screen: {
		route: 'MY_PLUGIN_SETTINGS',
		getComponent: () => MyScreen,
	},
});
```

<Warning>
	Entries are not cleaned up for you. To avoid leaving a dead route behind when your plugin is disabled:

	1. Call `registerSettings` in your plugin's `start`.
	2. Call `removeSettings` with the same key in `stop`.
</Warning>

### The entry shape

An entry uses the same shape as a route in Discord's `SETTING_RENDERER_CONFIG`.

<ParamField path="type" type="'route'" required>
	Always `'route'`. Routes are the only kind of entry Unbound registers.
</ParamField>

<ParamField path="key" type="string" required>
	Unique identifier for the entry. `removeSettings` deletes entries by this key. Built-ins use screaming snake case (`UNBOUND_GENERAL`). Namespace your keys so they can't collide.
</ParamField>

<ParamField path="useTitle" type="() => string" required>
	Hook that returns the title shown in the list and in the screen header. Because it's a hook, it can read from [i18n](/modules/i18n) or from storage and re-render when either changes.
</ParamField>

<ParamField path="parent" type="string | null" required>
	The key of the parent route, or `null` for a top-level entry. Built-ins pass `null`.
</ParamField>

<ParamField path="screen" type="SettingsScreen" required>
	The screen this route renders.

	<Expandable title="SettingsScreen">
		<ParamField path="route" type="string" required>
			The route name. Built-ins set this to the same value as `key`.
		</ParamField>

		<ParamField path="getComponent" type="() => ComponentType<any>" required>
			Returns the component to render. It's called lazily, so the component is resolved only when the screen opens.
		</ParamField>
	</Expandable>
</ParamField>

<ParamField path="section" type="string">
	The section label the entry is grouped under in the settings overview. Built-ins use `'Unbound'`.
</ParamField>

<ParamField path="usePredicate" type="() => boolean">
	Hook that decides whether the entry is shown. The built-in Developer page uses it to appear only while developer mode is on.
</ParamField>

<ParamField path="excludeFromDisplay" type="boolean">
	Hides the entry from the settings list but keeps the route navigable. Use it for screens you open from code, not ones the user picks from a list.
</ParamField>

<ParamField path="IconComponent" type="ComponentType<any>">
	Component rendered as the row's leading icon. Built-ins render Discord's `TableRowIcon` with an id resolved through [assets](/modules/assets).
</ParamField>

### Conditional and hidden entries

`usePredicate` is a hook, so it can subscribe to storage and show or hide the entry as settings change. The built-in Developer page uses this to appear only after developer mode is enabled.

```tsx
import { settings, storage, assets } from '@unbound-app/api';
import { Discord } from '@unbound-app/api/metro/components';

const store = storage.getStore('my-plugin');

settings.registerSettings({
	type: 'route',
	key: 'MY_PLUGIN_ADVANCED',
	useTitle: () => 'Advanced',
	usePredicate: () => store.useSettingsStore(({ key }) => key === 'advanced').get('advanced', false),
	IconComponent: () => <Discord.TableRowIcon source={assets.getIDByName('WrenchIcon')} />,
	parent: null,
	section: 'Unbound',
	screen: {
		route: 'MY_PLUGIN_ADVANCED',
		getComponent: () => AdvancedScreen,
	},
});
```

### Removing and inspecting

<CodeGroup>
```ts removeSettings
// Accepts any number of keys.
settings.removeSettings('MY_PLUGIN_SETTINGS', 'MY_PLUGIN_ADVANCED');
```

```ts sections
// The current registry, keyed by entry key.
const registered = settings.sections();
```
</CodeGroup>

<Note>
	`sections()` returns only entries registered through this API. Unbound's built-in screens are merged in separately when the navigation config is read, so they aren't in the result.
</Note>

### Settings vs storage

The two modules do different jobs:

| | [settings](/modules/settings) | [storage](/modules/storage) |
| --- | --- | --- |
| Owns | Screens in the settings navigation | Persisted values |
| Written to disk | No | Yes, to `settings.json` |
| Reactive | Via `useTitle` / `usePredicate` hooks | Via `useSettingsStore` and change events |

A settings screen almost always uses both. `settings` puts the screen in the list, and `storage` holds the values its controls read and write.

Build the screen itself from [components](/modules/components). See [creating an addon](/addons/creating) for where the registration goes in a plugin's lifecycle.

Addon enabled-state is persisted by the [managers](/modules/managers), not by this module.
