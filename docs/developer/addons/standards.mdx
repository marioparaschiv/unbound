Every plugin follows the same layout and loading rules, so anyone can open one and find their way. `ubd create` scaffolds a plugin that already follows them. Lint rules from `@unbound-app/cli/oxlint` and checks in `ubd build` catch most departures, and each rule below names its check.

## The layout

A plugin is split by **feature**: one thing the plugin does, in its own folder under `src/`. The entry file only starts features.

<FileTree>
	<Folder name='my-plugin'>
		<File name='manifest.json' note='The metadata Unbound reads' />
		<File name='ADDON.md' note='The store page' />
		<Folder name='media' note='Images and videos ADDON.md shows' />
		<Folder name='src'>
			<File name='index.tsx' note='Starts each feature. Nothing else' />
			<File name='settings.tsx' note='The settings panel' />
			<File name='constants.ts' />
			<File name='types.ts' />
			<Folder name='components' note='Components several features share' />
			<Folder name='<feature>' note='One folder per feature'>
				<File name='index.ts' note='Starts the feature, with its developer notes' />
				<File name='platform.ts' note='Picks the iOS or Android handler, if the feature has one' />
				<Folder name='ios' />
				<Folder name='android' />
				<Folder name='components' note="This feature's own components" />
			</Folder>
		</Folder>
	</Folder>
</FileTree>

- The only files at the root of `src/` are `index.tsx`, `settings.tsx`, `constants.ts` and `types.ts`. Every other file goes in a feature folder.
- Platform code goes in the `ios/` and `android/` folders of the feature it belongs to, never at the root of `src/`.

**Checked by** the build check `layout`. `ubd build` prints a warning for each departure. Warnings don't fail the build.

## Each feature starts itself

`src/index.tsx` calls each feature's start function. The feature then finds its own modules and makes its own patches. A feature makes only the patches it needs. The one exception is a patch on another module that only passes data to the feature, such as a value from a closure. That patch lives in the folder of the feature that uses the data.

```ts src/greeting/index.ts
import { metro, patcher } from '@unbound-app/api';

const Messages = metro.findByProps('sendMessage', 'receiveMessage');

/**
 * @description Logs each message the user sends.
 * Patches `sendMessage` on Discord's message actions module.
 */
export function startGreeting() {
	patcher.before(Messages, 'sendMessage', ({ args }) => logger.log('Sending to', args[0]));
}
```

Notes for the next developer go in the JSDoc of the feature's `index.ts`, as above. Name every patch the feature makes on another module, and every Discord module or store it depends on.

**Checked by** addon review.

## No eager lookups while the plugin loads

The top level of your files runs every time the plugin starts, before `start`. At launch, it delays Discord. A Metro search walks every module in Discord's bundle, so the top level makes no eager search: no `metro.find`, `findBy*` or `flux.getStore` with `{ lazy: false }`.

```ts
import { flux, metro } from '@unbound-app/api';

// Lazy: safe at the top of a file.
const Messages = metro.findByProps('sendMessage', 'receiveMessage');
const UserStore = flux.getStore('User');

// Eager: move it into the function that uses it.
const Button = metro.findByName('Button', { lazy: false });
```

**Checked by** the lint rule `unbound/no-module-scope-lookup`.

## `platform.ts` is the only platform check

A feature with platform code picks its handler once, in `platform.ts`. The rest of the feature calls the handler, and never checks the platform itself.

```ts src/greeting/platform.ts
import { definePlatform } from '@unbound-app/api/native';

import { platformName as android } from '~/greeting/android/platform-name';
import { platformName as ios } from '~/greeting/ios/platform-name';

export const platformName = definePlatform({ ios, android });
```

`ubd build` reads the keys you pass to `definePlatform` to learn which platforms the plugin supports.

**Checked by** the lint rule `unbound/platform-check-only-in-platform-file`, and the build check `layout`.

## Use the scoped API

Import from `@unbound-app/api`. In a plugin, those imports come from its [Addon scope](/docs/developer/plugins/introduction#the-addon-scope), which removes what the plugin registered when it stops. `window.unbound` is the unscoped API, so anything registered through it outlives the plugin.

**Checked by** the lint rule `unbound/no-window-unbound`.

## Never write Capabilities by hand

`ubd build` writes `platforms` and each platform's Capabilities into `dist/manifest.json`. It finds them by reading the native calls each platform handler can reach. Your own `manifest.json` never lists them.

**Checked by** the build check `capabilities`. A hand-written `capabilities` or `platforms` field fails the build, and so does a dynamic access such as `native.objc[name]`.

## Change native views from the UI thread

A plugin that changes how Discord's native views look makes the change from a worklet on the UI thread, so it never flashes in. See [Native UI Thread](/docs/developer/plugins/ui-thread).

**Checked by** addon review.

## Keep the bundle small

Every plugin's bundle loads on each start. Keep it under its budget, `50kb` by default, and import a library the client provides, such as `lodash`, by its name rather than by a file path, so the bundle doesn't carry a second copy.

**Checked by** the [build report](/docs/developer/development/cli#build-report). `ubd build` warns past a budget, and `--strict-budget` fails the build.

## Every check at a glance

`ubd build` runs these checks after it bundles a plugin. An error fails the build, and a warning is printed.

| Build check | Reports |
| --- | --- |
| `naming` | Warnings for a folder, id, name or description that breaks the [manifest](/docs/developer/addons/manifest) naming rules |
| `capabilities` | Errors for hand-written Capabilities or platforms, and for dynamic `native` access |
| `layout` | Warnings for each departure from [the layout](#the-layout) |
| `page` | Errors and warnings for an `ADDON.md` that breaks the [store page](/docs/developer/addons/store-page) rules |

`ubd check` runs these checks and the lint without building. See [the CLI](/docs/developer/development/cli#check-an-addon).

A scaffolded plugin's `.oxlintrc.json` turns on the three lint rules:

```json .oxlintrc.json
{
	"jsPlugins": [{ "name": "unbound", "specifier": "@unbound-app/cli/oxlint" }],
	"rules": {
		"unbound/no-window-unbound": "error",
		"unbound/platform-check-only-in-platform-file": "error",
		"unbound/no-module-scope-lookup": ["error", { "lazyByDefault": true }]
	}
}
```
