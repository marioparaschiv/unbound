Discord's screens are React components your plugin doesn't own. To change one, you patch the function that renders it, usually with an `after` patch, and edit the elements it returns. Your changes become part of Discord's real tree, so they can use its context and survive its re-renders.

Read [Patching Functions](/docs/developer/plugins/patching) first. This page applies the same patcher to components.

## Patching a render

A component renders through a function. Find the module that owns the component, patch that function with `after`, and return the tree you want.

```tsx src/toasts/index.tsx
import { metro, patcher } from '@unbound-app/api';

const Toasts = metro.findByProps('ToastContainer');

export function startToastPatch() {
	patcher.after(Toasts.ToastContainer, 'type', ({ result }) => {
		// wrap, replace, or return the original tree
		return result;
	});
}
```

## Where the render function lives

Each kind of component keeps its render function in a different place, so where you patch depends on the kind.

<Tabs>
	<Tab title='Memo'>
		`React.memo` wraps the real component and stores it on `.type`. Patch `.type`, not the wrapper. React calls the inner component, so a patch on the wrapper never runs.

		```tsx
		const { SomeMemoComponent } = metro.findByProps('SomeMemoComponent');

		patcher.after(SomeMemoComponent, 'type', ({ result }) => {
			return result;
		});
		```
	</Tab>
	<Tab title='Class'>
		A class component renders through `render` on its prototype. The instance is `this`, so you can read its `props` and `state`.

		```tsx
		const SomeClassComponent = metro.findByName('SomeClassComponent');

		patcher.after(SomeClassComponent.prototype, 'render', ({ this: instance, result }) => {
			logger.log('Rendering with', instance.props);

			return result;
		});
		```
	</Tab>
	<Tab title='Function'>
		A plain function component has no prototype and often no useful name, so Metro can't find it directly. Reach it through the parent that renders it:

		1. Patch the parent's render.
		2. Find the child in the parent's result.
		3. Patch the child from there.

		See [Reaching into a render](#reaching-into-a-render).
	</Tab>
</Tabs>

## Reaching into a render

A render result is a tree of React elements. On each element, `type` is the component, `props` its props, and `props.children` what it renders inside. Walk that tree to find the element you want.

```ts src/components/find-in-tree.ts
import { isValidElement, type ReactElement, type ReactNode } from 'react';

type Props = { children?: ReactNode; style?: unknown };

export function findInTree(
	node: ReactNode,
	matches: (element: ReactElement<Props>) => boolean,
): ReactElement<Props> | undefined {
	if (!isValidElement<Props>(node)) return undefined;
	if (matches(node)) return node;

	const { children } = node.props;

	for (const child of Array.isArray(children) ? children : [children]) {
		const found = findInTree(child, matches);

		if (found) return found;
	}

	return undefined;
}

export function isNamed(element: ReactElement, name: string): boolean {
	return typeof element.type === 'function' && element.type.name === name;
}
```

```tsx
patcher.after(Parent, 'type', ({ result }) => {
	const row = findInTree(result, (element) => isNamed(element, 'Row'));

	if (row) {
		row.props.style = [row.props.style, { opacity: 0.5 }];
	}

	return result;
});
```

Other plugins may patch the same component, so:

- Guard every lookup. `findInTree` returns `undefined` when Discord changes its tree, or another plugin already has.
- Add to `children` instead of replacing it. Replacing it removes what earlier plugins added.

## Patching a child for one render

Some children are created fresh on every parent render. A patch left on one targets a component that no longer exists on the next render. Patch it from inside the parent's patch instead, with `{ once: true }`, so the child's patch lasts for exactly one render.

```tsx
patcher.after(Parent, 'type', ({ result }) => {
	const child = findInTree(result, (element) => isNamed(element, 'Child'));

	if (child) {
		patcher.after(child.type, 'type', ({ result: childResult }) => childResult, { once: true });
	}

	return result;
});
```

## Cleaning up

Unbound removes your patches when the plugin stops. That restores Discord's render function, but not what's on screen. A component that already rendered with your patch keeps showing your output until React renders it again. So force a re-render when the plugin stops.

<Tabs>
	<Tab title='Class'>
		A class instance has `forceUpdate`. Keep the instance your patch saw, and call it in `stop`.

		```tsx src/index.tsx
		import { metro, patcher } from '@unbound-app/api';
		import type { Component } from 'react';

		const SomeClassComponent = metro.findByName('SomeClassComponent');
		let mounted: Component | undefined;

		export default {
			start() {
				patcher.after(SomeClassComponent.prototype, 'render', ({ this: instance, result }) => {
					mounted = instance;

					return result;
				});
			},
			stop() {
				patcher.unpatchAll();
				mounted?.forceUpdate();
			},
		};
		```
	</Tab>
	<Tab title='Function'>
		A function component has no `forceUpdate`. Re-rendering it isn't safe either. If your patch called hooks, the unpatched render calls fewer, and React throws `Rendered fewer hooks than expected`.

		Remount it instead. Give the element a new `key` from the parent that renders it. React then throws the old element away and mounts a fresh one, which runs Discord's original render from the start.
	</Tab>
</Tabs>

<Tip>
	Patch the smallest component that does the job. A patch on a large component that renders often runs your code on every render.
</Tip>
