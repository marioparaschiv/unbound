This page walks through `packages/plugins/character-counter`, the reference plugin. Character Counter shows `120/2000` above the composer while you type, and it uses every part of the plugin setup once: a feature folder, settings, translations, tests and a store page. Every code block marked with its path is copied from that plugin, and a test fails when a copy drifts from the file.

Read [How Plugins Run](/docs/developer/plugins/introduction) first for the lifecycle. The [Project Layout](/docs/developer/addons/standards) page lists the rules that this layout follows and the checks behind them.

A plugin that ships images adds `assets/`, and a store page with a banner adds `media/`. Both are covered below. `dist/` and `node_modules/` are build output and installs, and Git ignores them.

## The files at the root

### manifest.json

The [manifest](/docs/developer/addons/manifest) is the source of truth for the plugin's identity. `main` names the entry file inside `src/`, and `icon` names one of Discord's own icons.

```json manifest.json quoted
{
	"id": "unbound.character-counter",
	"name": "Character Counter",
	"description": "Shows the current message length and Discord's character limit in the composer.",
	"authors": [
		{
			"name": "thororen",
			"id": "848339671629299742"
		},
		{
			"name": "creations",
			"id": "209830981060788225"
		},
		{
			"name": "adrian",
			"id": "224617799434108928"
		}
	],
	"version": "1.0.4",
	"icon": "TextIcon",
	"main": "index.tsx"
}
```

The manifest has no `platforms` or Capabilities. `ubd build` finds them by reading the native calls the plugin can reach, and it fails the build when you write them by hand.

### rollup.config.mjs and package.json

The build is one call. `unbound` reads the manifest, bundles `src/`, generates the settings and i18n modules, and runs the build checks.

```js rollup.config.mjs quoted
import { unbound } from '@unbound-app/cli/rollup';

export default unbound(import.meta.url);
```

`package.json` sets `"type": "module"` and two scripts, `build` and `test`. Its `devDependencies` carry the types: `@unbound-app/api` for the API, `@types/react` and `react-native` for the components, and `@unbound-app/cli` for the build. Its `dependencies` hold `@unbound-plugins/shared`, the helpers first-party plugins share. A third-party plugin has no such dependency and writes those few helpers itself.

### tsconfig.json

```json tsconfig.json quoted
{
	"extends": "../tsconfig.json",
	"compilerOptions": {
		"types": ["bun", "@unbound-app/api/global"],
		"paths": {
			"~/*": ["./src/*"]
		}
	},
	"include": ["src", "tests", "settings.ts"]
}
```

`@unbound-app/api/global` declares the globals of the [Addon scope](/docs/developer/plugins/introduction#the-addon-scope), such as `logger` and `addon`. The `~/*` path is why every import across folders reads `~/counter/limit` and not `../../limit`. The build resolves the same alias.

### bunfig.toml

One line turns on the testing preset, which stands in for Unbound, Discord and the build while `bun test` runs.

```toml bunfig.toml quoted
[test]
# Serves the plugin's manifest, translations, settings and a fake Unbound API to every test.
preload = ["@unbound-app/api/testing/preset"]
```

See [Testing](/docs/developer/plugins/testing) for what the preset serves.

## The entry

`src/index.tsx` starts the plugin's features and holds no logic of its own. A plugin with several features calls each feature's start function here.

```tsx src/index.tsx quoted
import { featureSelfTest } from '@unbound-plugins/shared/lifecycle/health';

import { startCounter } from '~/counter';

export function start() {
	startCounter();
}

export { featureSelfTest as selfTest };
```

There is no `stop`. The patch that `startCounter` makes goes through the plugin's own `patcher`, so the Addon scope removes it after the plugin stops, and nothing else needs undoing. Add a `stop` only for what the scope cannot see, as [How Plugins Run](/docs/developer/plugins/introduction#what-stop-still-has-to-undo) lists.

`selfTest` is the optional fourth lifecycle export. The device matrix calls it after a restart, and it returns `{ ok, detail }`. A plugin whose `start` skipped every feature, because a module was not found, still passes `start`. The self-test is what fails it. `featureSelfTest` reports `ok` once at least one feature has called `recordApplied`, and says why when a feature recorded a skip or a failure. Both come from `@unbound-plugins/shared`.

A plugin with more than one feature starts them with `startFeatures` or `applyFeatures`, which are also in `@unbound-plugins/shared/lifecycle`:

| Helper | When a feature throws | Use it when |
| --- | --- | --- |
| `startFeatures(name, features)` | Logs it and records a failure. The other features still start | The features are independent, which is the usual case |
| `applyFeatures(name, features)` | Removes the features already applied, then rethrows | The features need each other, so half of them is worse than none |

Each takes functions that start one feature and may return a cleanup. Both return one function that runs every cleanup in reverse. Return it from `stop`.

## A feature folder

A [feature](/docs/developer/addons/standards#the-layout) is one thing the plugin does. It lives in its own folder under `src/`, and it starts itself, so the entry never needs to know how. Character Counter has one, `src/counter/`.

### index.tsx: start the feature

The feature's `index.tsx` makes its patch. The JSDoc names what it patches and what it reads, so the next developer can find the Discord code it depends on.

```tsx src/counter/index.tsx quoted
import { recordApplied } from '@unbound-plugins/shared/lifecycle/health';
import ensureModules from '@unbound-plugins/shared/metro/ensure-modules';
import { cloneElement, isValidElement, type ReactNode } from 'react';
import { patcher } from '@unbound-app/api';

import { ChatInputs, FloatingChatInputContainer, SelectedChannelStore } from '~/counter/modules';
import { CharacterCounter } from '~/counter/components/character-counter';

type ContainerProps = { channel?: { id?: string }; channelId?: string };

/**
 * @description Shows the counter above the composer without changing the composer's layout.
 * Patches the render of `FloatingChatInputContainer`, reads the draft from `ChatInputs`, and the
 * Nitro tier from `UserStore`. The Addon scope removes the patch when the plugin stops.
 */
export function startCounter(): void {
	if (!ensureModules('Character Counter', { ChatInputs, FloatingChatInputContainer })) return;

	patcher.react.after(FloatingChatInputContainer, 'default', ({ props, result }) => {
		const container: ContainerProps = props;
		const channelId =
			container.channel?.id ?? container.channelId ?? SelectedChannelStore.getChannelId();

		if (!channelId || !isValidElement<{ children?: ReactNode }>(result)) return;

		return cloneElement(
			result,
			{},
			<>
				{result.props.children}
				<CharacterCounter key='character-counter' channelId={channelId} />
			</>,
		);
	});

	recordApplied(1);
}
```

Three habits of this file recur in every plugin:

- `ensureModules` checks that the modules the feature needs exist, and logs one line and returns `false` when one does not. The feature then does nothing, and the rest of the plugin keeps working. `ensureModules` never loads a lazy handle.
- `patcher.react.after` takes the module and the key `'default'`, not the component itself. Reading the component would load the module at start. With the key, the patch waits for the module.
- `recordApplied(1)` tells the self-test that this feature applied.

The patch adds a child and leaves Discord's tree otherwise as it was. Other plugins can patch the same component, so it never replaces `children`.

### modules.ts: every lookup in one place

Every handle to something outside the plugin goes in the feature's `modules.ts`. When Discord renames a module, the fix is one line in one file.

```ts src/counter/modules.ts quoted
import { flux, metro } from '@unbound-app/api';

export const ChatInputs = metro.findByProps('getBestActiveInputForChannelId');
export const FloatingChatInputContainer = metro.findByFilePath(
	'modules/chat_input/native/FloatingChatInputContainer.tsx',
);

export const SelectedChannelStore = flux.getStore('SelectedChannel');
export const ChannelStore = flux.getStore('Channel');
export const UserStore = flux.getStore('User');
```

All of these lookups are lazy. Each one returns a stand-in at once and searches the first time something reads from it, so the top level of this file costs nothing at launch. `flux.getStore` is typed, so `UserStore.getCurrentUser()` has a type. A lookup that Unbound already did needs no search of its own: prefer `metro.api`, `metro.common` and `metro.stores` where they hold what you need, as [Finding Modules](/docs/developer/plugins/metro#modules-unbound-already-found) lists. `components/character-counter.tsx` reads `metro.common.Theme` for that reason.

### limit.ts: logic with no Discord in it

Logic that decides something goes in a plain file with no API imports. It is the part of the plugin that tests reach most easily.

```ts src/counter/limit.ts quoted
import type { FluxUser } from '@unbound-app/api/flux';

export type CounterTone = 'primary' | 'muted' | 'yellow' | 'orange' | 'red';

/**
 * @description Discord's message length limit for a user.
 * @param user The signed-in user; a `premiumType` of `2` is Nitro.
 * @returns 4000 for Nitro, otherwise 2000.
 */
export function characterLimit(user: Pick<FluxUser, 'premiumType'> | undefined): number {
	return user?.premiumType === 2 ? 4000 : 2000;
}

/**
 * @description Picks the counter's color as the message approaches the limit.
 * @param length The message length.
 * @param limit The user's message length limit.
 * @param colorEffects Whether the warning colors are turned on.
 * @returns `primary` when warnings are off, otherwise a tone for the share of the limit used.
 */
export function counterTone(length: number, limit: number, colorEffects: boolean): CounterTone {
	if (!colorEffects) return 'primary';

	const used = length / limit;

	if (used < 0.5) return 'muted';
	if (used < 0.75) return 'yellow';
	if (used < 0.9) return 'orange';

	return 'red';
}
```

`colors.ts` holds the same kind of logic for theme colors, and `use-draft-length.ts` is the hook that reads the draft.

### components: what is drawn

The pill is a React component in `components/`. It reads three things: the draft through `useDraftLength`, the Nitro tier through `flux.useStore`, and the user's setting through `useSetting`.

```tsx src/counter/components/character-counter.tsx excerpt
	const length = useDraftLength(channelId);
	const limit = flux.useStore(UserStore, (store) => characterLimit(store.getCurrentUser()));
	const colorEffects = useSetting('colorEffects');
```

The accessibility label is the plugin's one translated string that has a placeholder:

```tsx src/counter/components/character-counter.tsx excerpt
				<Text
					accessibilityLabel={format('COUNTER_LABEL', { length, limit })}
```

The build adds the hook that redraws the component when the user changes language, so `format` needs nothing else.

### constants.ts

A constant that more than one file reads goes in `src/constants.ts`. A value one file uses stays in that file.

```ts src/constants.ts quoted
// Each tone tries Discord's theme tokens in order, then a fixed color when the theme has none.
export const TONE_COLORS = {
	primary: { tokens: ['BRAND_330', 'BRAND_500'], fallback: '#5865f2' },
	muted: { tokens: ['TEXT_NORMAL'], fallback: '#f2f3f5' },
	yellow: { tokens: ['YELLOW_330', 'YELLOW_300'], fallback: '#fee75c' },
	orange: { tokens: ['ORANGE_330', 'ORANGE_300'], fallback: '#f0b232' },
	red: { tokens: ['RED_360', 'RED_400'], fallback: '#ed4245' },
};

export const COUNTER_HEIGHT = 20;
```

## Settings

`settings.ts` sits beside `src/`, not in it. The build reads it, and it never ships in the bundle. One setting here becomes a switch in the settings panel, with no panel code.

```ts settings.ts quoted
import { defineSettings, setting } from '@unbound-app/settings/schema';

export default defineSettings(
	{
		colorEffects: setting.boolean({
			default: true,
			title: 'COLOR_THRESHOLDS',
			subtitle: 'COLOR_THRESHOLDS_SUBTITLE',
		}),
	},
	{ title: 'APPEARANCE' },
);
```

`title` and `subtitle` are keys of `i18n/en-US.json`, not text. The build writes `src/unbound-settings.d.ts` from this file, which is why `useSetting('colorEffects')` above returns a `boolean`. See [Settings and Storage](/docs/developer/plugins/settings) for the builders.

## Translations

`i18n/en-US.json` holds every string the plugin shows. Other languages are more files beside it, and each may leave keys out.

```json i18n/en-US.json quoted
{
	"APPEARANCE": "Appearance",
	"COLOR_THRESHOLDS": "Color thresholds",
	"COLOR_THRESHOLDS_SUBTITLE": "Warn as the message approaches Discord’s character limit.",
	"COUNTER_LABEL": "{length} of {limit} characters"
}
```

The build writes `src/unbound-i18n.d.ts` from it, so a key that is not here is a type error in `format`, in a setting's `title` and in every toast. Commit both generated files, so your editor knows the keys before the first build. See [Translations](/docs/developer/plugins/i18n).

## Tests

The tests sit in `tests/`, named after what they cover. Two kinds appear here.

Logic with no Discord in it is tested directly. This needs the preset only for the `~/` alias.

```ts tests/counter/limit.test.ts quoted
import { describe, expect, test } from 'bun:test';

import { characterLimit, counterTone } from '~/counter/limit';

describe('characterLimit', () => {
	test('uses Discord message limits for standard and Nitro accounts', () => {
		expect(characterLimit({ premiumType: 0 })).toBe(2000);
		expect(characterLimit(undefined)).toBe(2000);
		expect(characterLimit({ premiumType: 2 })).toBe(4000);
	});
});

describe('counterTone', () => {
	test('moves through warning colors as the limit approaches', () => {
		expect(counterTone(999, 2000, true)).toBe('muted');
		expect(counterTone(1000, 2000, true)).toBe('yellow');
		expect(counterTone(1500, 2000, true)).toBe('orange');
		expect(counterTone(1800, 2000, true)).toBe('red');
	});

	test('stays on the primary color when warnings are off', () => {
		expect(counterTone(1950, 2000, false)).toBe('primary');
	});
});
```

The started plugin is tested through the preset. `character-counter.test.tsx` registers the Discord modules the plugin looks up, calls `startPlugin()`, renders the patched container, and reads the pill. It checks what a user sees: the text, the limit with Nitro, and the color at 90%.

```tsx tests/character-counter.test.tsx excerpt
	test('shows the length over the limit while a message is written', () => {
		draft.text = 'hello';

		const counter = renderComposer().find('Text');

		expect(counter.text()).toBe('5/2000');
		expect(counter.props.accessibilityLabel).toBe('5 of 2000 characters');
	});
```

The preset forgets every registered module before each test, so the file registers them again in `beforeEach`. [Testing](/docs/developer/plugins/testing) covers the preset and the fakes.

## Images

A plugin that ships images keeps them in an `assets/` folder beside `src/`. Importing one gives its asset id, and the build copies the file into `dist/`. Character Counter has none, because it draws only text. See [Images](/docs/developer/plugins/assets).

## The store page

`ADDON.md` is what the store shows for the plugin. It has no title, because the store takes the title and summary from the manifest.

```md ADDON.md quoted
---
banner: media/banner.png
---

## :sparkle: What it does

- :text: Shows length over your limit, like `120/2000`, while you type.
- :star: The limit is 4000 characters with Nitro and 2000 without.
- :eye: Hides while the chat input is empty and never changes its layout.
- :arrow-up: Moves up to clear the slowmode notice in channels that have one.

## :gear: Settings

- :color-palette: **Color thresholds** turns the counter yellow at 50% of the limit, orange at 75% and red at 90%. Off, it stays in Discord's brand color. On by default.
```

The frontmatter names the banner, `media/banner.png`, and can add a gallery. All of it lives in a `media/` folder beside `ADDON.md`. A page with no frontmatter builds with a warning, and the store shows no banner. First-party banners come from `bun run plugins:banners`, which draws one from the manifest's name, description and icon and leaves a hand-made banner alone. [Store Page](/docs/developer/addons/store-page) lists the rules for the banner, the gallery and the `:name:` icons.

`CHANGELOG.md` lists what changed in each version, newest first, and the version in it matches `manifest.json`.
