A plugin is a bundle of JavaScript that Unbound loads and runs inside Discord. It finds Discord's code with Metro, changes it with the patcher, and saves options with storage. This page covers what happens to that bundle from the moment the user turns it on.

## The shape of a plugin

A plugin's entry file exports its lifecycle as named functions. Every export is optional: a plugin that only patches at the top level of its files needs none.

```tsx src/index.tsx
export function start() {
	// set up patches, listeners and commands
}

export function stop() {
	// undo what the Addon scope can't see
}

export function SettingsPanel() {
	return <Settings />;
}
```

| Export | Type | When Unbound uses it |
| --- | --- | --- |
| `start` | `(context) => void \| Promise<void>` | When the plugin is turned on, and at launch if it was on. A rejected promise counts as a failed start |
| `stop` | `() => void \| Promise<void>` | When the plugin is turned off. A returned promise is awaited |
| `SettingsPanel` | A React component | Rendered as `<SettingsPanel />` when the user opens the plugin's settings. See [Settings and Storage](/docs/developer/plugins/settings) |

The build checks the entry against this table:

- A default export fails the build. Export `start` and `stop` as named functions instead, or run `ubd migrate entry` to rewrite an old `export default { start, stop, getSettingsPanel }` entry.
- A misspelt lifecycle name, such as `Start`, `onStart` or `getSettingsPanel`, fails the build with the name to use.
- A `stop` that takes parameters, or an `async` `SettingsPanel`, fails the build.
- Any other export prints a warning. Unbound does not read it. Put settings button handlers in `src/actions.ts`.

A plugin built before named exports still runs: Unbound reads its default object's `start`, `stop` and `getSettingsPanel`, and in a developer build logs one note asking you to rebuild it.

The settings button on the plugin's card shows while the plugin has a panel, and opens it only while the plugin runs. It is disabled while an async `start` or `stop` is in flight or after a failed start. If the plugin stops while its panel is open, the panel closes into a notice.

## The lifecycle

Each time the plugin starts, Unbound evaluates its bundle again with a fresh Addon scope, then calls the exported `start`. When the user turns it off, Unbound calls `stop`, then disposes the scope.

<Flow>
	<FlowStep title='Evaluate' detail='Top-level code runs' />
	<FlowStep title='start()' detail='Set everything up' />
	<FlowStep title='Running' />
	<FlowStep title='stop()' detail='Undo the rest' />
	<FlowStep title='Scope disposed' detail='Removes what it recorded' added />
</Flow>

The top level of your files runs during evaluation, before `start`. At launch, that delays Discord itself, so keep it cheap.

<Warning>
	Make no eager [Metro](/docs/developer/plugins/metro) search at the top level. Any search with `{ lazy: false }` walks every module right away. `metro.find`, the `findBy*` helpers and `flux.getStore` are lazy by default, so they're safe there.
</Warning>

## The Addon scope

Each plugin runs with its own **Addon scope**: a set of globals that belong to it. Everything the plugin registers through them is recorded. After `stop` returns, the scope removes it all, newest first. So `stop` only has to undo what the scope can't see.

| Global | What it is |
| --- | --- |
| `unbound` | The API. Its `patcher`, `commands`, `metro`, `storage`, `flux`, `settings` and `assets` are the plugin's own versions |
| `addon` | The plugin's handle: `id`, `name`, `version`, `manifest` and its state |
| `logger` | A logger that prefixes every line with the plugin's name |
| `setTimeout`, `setInterval` | Timers that are cleared when the plugin stops |
| `React` | React |

Imports from `@unbound-app/api` read from the scoped `unbound`. So `import { patcher } from '@unbound-app/api'` gives the plugin its own patcher. The scope removes:

- Patches and slash commands.
- Timers from `setTimeout` and `setInterval`.
- Listeners from `metro.onModuleLoad`, and `metro.findLazy` waits that haven't resolved.
- Listeners from `storage.onChange`.
- Listeners and interceptors from `flux.onStoreChange`, `flux.onAction` and `flux.interceptAction`.
- Settings sections from `settings.registerSection`.
- Listeners from `assets.onAssetRegistered`.

```ts src/channel-log/index.ts
import { flux, storage } from '@unbound-app/api';

const settings = storage.getBucket();

export function startChannelLog() {
	flux.onAction('CHANNEL_SELECT', ({ channelId }) => {
		settings.set('lastChannel', channelId);
		logger.log('Selected', channelId);
	});
}
```

This feature needs no `stop`. The scope removes the Flux listener when the plugin stops.

### What `stop` still has to undo

The scope only sees what went through it. Undo these yourself:

- A listener you added straight to a Discord module.
- A built-in you registered with `builtins.register`.
- A settings section of Discord's or Unbound's that you removed. The scope can't restore it.
- A change a patch callback made outside the render, such as a value it wrote onto a Discord object. Mounted components re-render on their own, as [Undoing a component patch](/docs/developer/plugins/react-patching#undoing-a-component-patch) explains.

Themes, icon packs and fonts ship no code, so they have no scope.

## Keeping a plugin fast

A plugin should cost almost nothing until it's used. Two habits get you there.

<Steps>
	<Step title='Keep lookups lazy' icon='clock'>
		Declare Metro lookups with the lazy `findBy*` helpers. The search runs the first time you read from the result, inside `start` or later in a handler.

		```ts
		const Messages = metro.findByProps('sendMessage', 'receiveMessage');
		```
	</Step>
	<Step title='Load heavy code on demand' icon='code-branch'>
		Move code that pulls in many modules into its own file, and `import()` it inside `start`. That code then loads only when the plugin runs.

		```ts src/index.tsx
		export async function start() {
			const { startEditor } = await import('~/editor');

			startEditor();
		}
		```
	</Step>
</Steps>
