Your plugin's tests run with `bun test`, on your computer, not on a phone. The testing preset of `@unbound-app/api` stands in for everything a plugin gets at runtime, so a test imports your code as it is and checks what it did.

## Reference

Import these from `@unbound-app/api/testing`.

| Export | What it does |
| --- | --- |
| `startPlugin(context?)` | Imports `src/index.tsx` and runs its `start` with a `PluginContext`, as Unbound does |
| `stopPlugin()` | Runs `stop`, then removes what the Addon scope recorded. Rejects when something is left |
| `pluginHolds()` | Lists each patch, command, listener and timer added since `startPlugin()` and still held |
| `render(element, options?)` | Draws a component with React's real hooks. `options`: `settings`, `locale`, `stores`. Returns `find`, `findAll`, `text`, `rerender`, `unmount`, `act` |
| `setLocale(locale)` | Changes the language for the rest of the test |
| `extendApi(namespace, members)` | Adds or replaces members of a fake, such as `'metro.components'` |
| `toasts.shown` | The options of each toast, in order. A shorthand such as `toasts.success('SAVED', vars)` also records its `key` and `vars`, with `title` in the active locale |
| `dialogs.opened` | Each dialog, with its title `key` for `confirm` and `alert`, and `respond(answer)` to press a button |
| `commands.registered`, `commands.run(path, options?, context?)` | The registered commands by name, and a call as if the user sent it |
| `patches.applied` | Each patch still held: its `kind`, `target` and `method`, and `pending`, which is `true` while it waits for its module |
| `flux.dispatched`, `flux.seed(stores)`, `flux.emit(name)`, `flux.dispatch(action)` | The actions the plugin dispatched, the stores a test seeds, and a way to send an action to the plugin's listeners |
| `logs.entries` | Each line the plugin's `logger` wrote |
| `metro.register(module, path?)` | Gives the plugin a Discord module to find |
| `native` | The fake native bridge. See [Testing Native Code](/docs/developer/plugins/testing-native) |
| `plugins`, `fs` | The plugins a test sets, and the in-memory files. See [Other plugins](#other-plugins) and [Files](#files) |

Each recorder shows only the current test. The rest of this page says when to use each.

## Turn on the preset

Add one line to `bunfig.toml` beside your `manifest.json`:

```toml bunfig.toml
[test]
preload = ["@unbound-app/api/testing/preset"]
```

Before your tests load, the preset reads your plugin's files and serves:

| Import | What a test gets |
| --- | --- |
| `@unbound-app/i18n` | Your real `i18n/*.json`, with an ICU formatter for `format`. en-US until you switch |
| `@unbound-app/settings` | Your `settings.ts`, with its defaults, saved to an in-memory Bucket |
| `@unbound-app/api` | A fake Unbound that records what your plugin did: patches, commands, toasts, dialogs, Flux, assets. It also fakes `metro` (with `api`, `stores`, `common`, `components` and `filters`), `native`, `plugins`, `ui`, `utils` and `fs` |
| `@unbound-app/api/metro/components` and every other subpath, such as `/ui` and `/utils/react` | The same fakes, imported by path |
| `react-native` | Each primitive, such as `View` and `Text`, as a plain node a test can find by name, with `Animated`, `Share`, `Dimensions`, `NativeEventEmitter`, `processColor`, `AccessibilityInfo`, `AppRegistry`, `AppState` and `NativeModules`. Your plugin needs no `react-native` install to run tests |
| `*.png`, `*.svg`, `*.svg?asset` | A stable asset id for an image, and a component for an SVG |

It also installs the plugin scope: `addon` from your manifest, `patcher`, `commands`, `logger`, `React`, and the scoped `setTimeout`, `setInterval` and their clears.

Before each test, it puts every fake back: no patches, commands, listeners, timers, Discord modules registered with `metro.register`, files, toasts or dialogs, settings at their defaults, the platform iOS, and en-US. A lookup your plugin made at import, such as `metro.findByProps('sendMessage')`, finds the modules a test registers next. You write no setup of your own.

## A first test

```ts tests/index.test.ts
import { startPlugin, stopPlugin, toasts } from '@unbound-app/api/testing';
import { settings } from '@unbound-app/settings';
import { expect, test } from 'bun:test';

test('greets with the plugin name', async () => {
	await startPlugin();

	expect(toasts.shown).toMatchObject([{ content: 'My Plugin is running.' }]);
	await stopPlugin();
});

test('stays quiet when greetOnStart is off', async () => {
	settings.greetOnStart = false;
	await startPlugin();

	expect(toasts.shown).toEqual([]);
	await stopPlugin();
});
```

The second test turns `greetOnStart` off. The first test is not affected, and neither is any test after it.

## Start and stop the plugin

`startPlugin()` imports `src/index.tsx` (or `src/index.ts`) and runs its `start` with a `PluginContext`, as Unbound does when the plugin is turned on. `stopPlugin()` runs its `stop`.

`stopPlugin()` then does what Unbound does after `stop`: it removes what the plugin scope recorded. That is every patch made with `patcher`, every command, every `flux`, `metro`, `storage` and `assets` listener, and every timer from the scoped `setTimeout` and `setInterval`. A plugin whose `stop` forgets one of these passes, as it does on a phone.

What the scope does not remove is a leak. `stopPlugin()` rejects, which fails the test, when something is left. The one thing the fake can see is a change listener added straight to a Flux store:

```txt
My Plugin left 1 thing(s) behind after stop():
  - UserStore.addChangeListener
```

Use `flux.onStoreChange(store, listener)` instead, which Unbound removes for you.

To check that a feature undid itself without stopping the plugin, such as when a setting turns it off, read `pluginHolds()`. It lists each patch, command, listener and timer added since `startPlugin()` and still held:

```ts
import { pluginHolds, startPlugin } from '@unbound-app/api/testing';
import { settings } from '@unbound-app/settings';
import { expect } from 'bun:test';

await startPlugin();
expect(pluginHolds()).toContain('flux.onAction(MESSAGE_CREATE)');

settings.greetOnStart = false;
expect(pluginHolds()).toEqual([]);
```

Pass a context to `startPlugin` to change what `start` receives: its `platform`, its `capabilities`, or the members of the `native` bridge your plugin calls. Every other bridge member is an empty object.

```ts
import { startPlugin } from '@unbound-app/api/testing';

await startPlugin({ capabilities: ['native.ffi.call'], native: { apiVersion: '2.0.0' } });
```

## Test the self-test

A plugin can export `selfTest`, which the device matrix calls after a restart to learn whether the plugin works. A plugin whose features all skipped, because Discord renamed a module, still passes `start`, so the self-test is what fails it. First-party plugins count their applied features with `recordApplied` and export `featureSelfTest` from `@unbound-plugins/shared`, as [Anatomy of a Plugin](/docs/developer/plugins/anatomy#the-entry) shows. The same idea needs no helper:

```tsx src/index.tsx
import { flux, patcher } from '@unbound-app/api';

const UserStore = flux.getStore('User');
let applied = 0;

export function start() {
	patcher.after(UserStore, 'getCurrentUser', ({ result }) => result);
	applied++;
}

export function selfTest() {
	return { ok: applied > 0, detail: `${applied} features applied` };
}
```

Import `selfTest` from `~/index` in a test, start the plugin, and read the result:

```ts tests/self-test.test.ts
import { startPlugin } from '@unbound-app/api/testing';
import { expect, test } from 'bun:test';

import { selfTest } from '~/index';

test('reports that a feature applied', async () => {
	await startPlugin();

	expect(await selfTest()).toMatchObject({ ok: true });
});
```

State kept in a module, such as `applied`, survives from one test to the next. Reset it in `beforeEach`. The shared helper does this with `resetHealth()` from `@unbound-plugins/shared/lifecycle/health`.

## Check what the plugin did

Each recorder in the [reference](#reference) shows only the current test.

Run a command as if the user sent it. `run` takes its name, its options already parsed, and, optionally, the channel and guild:

```ts
import { commands, startPlugin } from '@unbound-app/api/testing';
import { expect } from 'bun:test';

const user = { id: '1', username: 'wumpus' };

await startPlugin();
expect(await commands.run('star', { user })).toEqual({ ephemeral: true, content: 'Starred wumpus.' });
```

Answer a dialog with `respond`. `true` confirms, or presses the first button. `false` cancels. A string presses the button with that label.

```ts
import { dialogs } from '@unbound-app/api/testing';
import { expect } from 'bun:test';

declare function clearHistory(): Promise<boolean>;

// clearHistory() asks with dialogs.confirm before it deletes.
const cleared = clearHistory();

dialogs.opened[0]?.respond(true);
expect(await cleared).toBe(true);
```

Give the plugin a Discord module to find with `metro.register`, before it starts:

```ts
import { metro, patches, startPlugin } from '@unbound-app/api/testing';
import { expect } from 'bun:test';

const MessageActions = { sendMessage: (content: string) => content };

metro.register(MessageActions);
await startPlugin();
expect(patches.applied).toMatchObject([{ kind: 'before', method: 'sendMessage' }]);
```

Patch a lookup made before its module registers, and the patch waits as it does on a phone. It applies when a test registers a module the lookup finds, in this test or a later one, and a patch removed first never applies. `patches.applied` lists it with `pending: true` until then, and `stopPlugin` removes it like any other. `patcher.react` waits the same way.

```ts
import { metro as fake } from '@unbound-app/api/testing';
import { metro, patcher } from '@unbound-app/api';

const Messages = metro.findByProps('sendMessage'); // at import, or in start()

patcher.after(Messages, 'sendMessage', () => 'patched'); // waits: no module yet
fake.register({ sendMessage: () => 'sent' }); // applies now
```

## Fake Discord

Your plugin finds Discord's code with `metro`. In a test, `metro` finds only what the test registers. Each module the plugin reaches by name is found by the same props as on a phone:

| Namespace | Fake |
| --- | --- |
| `metro.api` | `Messages`, `Linking`, `Profiles`, `AsyncUsers`, `Invites`, `OAuth2`, `ActionSheets` and `UserProfiles`, each found once a test registers a module with those props |
| `metro.common` | The same, such as `Theme`, `Clipboard` and `Moment`. `React` and `ReactNative` are the fakes |
| `metro.stores` | `Accessibility`, `Theme`, `Users` and `Guilds`, the stores a test seeds with `flux.seed` |
| `metro.components` | See below |
| `metro.filters` | `byProps`, `byName`, `byDisplayName`, `byTypeName`, `byFilePath`, `all`, `any` and `not` |

Finders return a lazy handle, as on device, so a module a later test registers is found. `{ lazy: false }` returns the module now, and `{ all: true }` every match. `any`, `all` and `not` reject a `byFilePath` filter, as the client does.

```ts
import { metro } from '@unbound-app/api/testing';

metro.register({ sendMessage: () => {}, receiveMessage: () => {} });
// Messages from `metro.api` is now the module above.
```

`@unbound-app/api/metro/components` imports in tests. `Discord`, `Forms`, `BottomSheets` and the other modules give any component by name, such as `Discord.Text` or `BottomSheets.ActionSheetRow.Icon`. Each draws its children, and `find('Text')` or `find('ActionSheetRow.Icon')` reaches it with its props. A `Discord.Button` also draws its `text`, and a `RowButton` or `TableRow` its `label` and `subLabel`, so `text()` and `find` see them. `Discord.createStyles(styles)` returns a hook that gives `styles`, calling a factory with no theme. To replace one, assign it: `Discord.Text = MyText`.

`@unbound-app/api/ui` works the same: `SwitchRow`, `Page`, `SchemaPanel` and the other rows draw their children and are found by name.

`utils` and `utils.react` are the client's own: `findComponent`, `filterComponents`, `findInTree`, `filterInTree`, `shallow` and `useShallow`.

### Native

`native` follows the platform a test sets, and fakes the Objective-C and Java bridges. [Testing Native Code](/docs/developer/plugins/testing-native) covers them.

### Other plugins

`plugins.get(id)`, `getAll`, `isEnabled`, `entities` and `errors` read the plugins a test sets. The plugin under test is there, started and enabled. Add or change another with the `plugins` recorder:

```ts
import { plugins } from '@unbound-app/api/testing';

plugins.set('chat-bubbles', { name: 'Chat Bubbles', enabled: true });
plugins.set('chat-bubbles', { started: false });
plugins.set('broken', { error: new Error('boom') }); // `failed`, and in `plugins.errors`
plugins.remove('chat-bubbles');
```

`enable`, `disable`, `toggle`, `start` and `stop` change what the handles report. `install`, `reload` and `update` settle at once and change nothing.

### Files

`fs` keeps files in memory, under `/documents`, which is `fs.documentsPath` for the plugin. Read or add to them in a test with the `fs` recorder:

```ts
import { fs } from '@unbound-app/api/testing';

fs.files.set('/documents/notes.txt', 'hi');
```

### Add to a fake

`mock.module('@unbound-app/api', ...)` in a test replaces the whole module, and with it every fake above. To add or replace members, use `extendApi` with the namespace, or a nested one with dots:

```ts
import { extendApi } from '@unbound-app/api/testing';

declare const MyComponent: () => null;

extendApi('metro.components', { Extra: MyComponent });
extendApi('metro', { custom: { value: 1 } });
```

It throws when the fake has no such namespace.

## Render a component

`render` draws a component with React's real hooks. It returns:

| Member | Does |
| --- | --- |
| `find(match)` | The first node that matches. It throws, naming what did render, when none does |
| `findAll(match)` | Every node that matches |
| `text()` | All the text rendered, joined |
| `rerender(element)` | Draws a new element in place. State is kept |
| `unmount()` | Removes the tree and runs each effect's cleanup |
| `act(callback)` | Runs an interaction, then draws once |

`match` is a name or a function. A name is a `react-native` primitive, such as `'Text'`, or a component's `displayName` or function name. A function gets each node and returns `true` for a match. Each node has `props`, `children`, `parent`, and its own `find`, `findAll` and `text`.

```tsx src/components/star-count.tsx
import { useSetting } from '@unbound-app/settings';
import { Pressable, Text } from 'react-native';
import { flux } from '@unbound-app/api';
import { useState } from 'react';

const UserStore = flux.getStore('User');

export default function StarCount() {
	const [stars, setStars] = useState(0);
	const accent = useSetting('appearance.accent');
	const username = flux.useStore(UserStore, (store) => store.getCurrentUser()?.username);

	return (
		<Pressable onPress={() => setStars(stars + 1)}>
			<Text style={{ color: accent }}>
				{username}: {stars} {stars === 1 ? 'star' : 'stars'}
			</Text>
		</Pressable>
	);
}
```

```tsx tests/star-count.test.tsx
import { render } from '@unbound-app/api/testing';
import { expect, test } from 'bun:test';

import StarCount from '~/components/star-count';

test('counts each press', () => {
	const view = render(<StarCount />, {
		settings: { appearance: { accent: '#FF0000' } },
		stores: { User: { getCurrentUser: () => ({ id: '1', username: 'wumpus' }) } },
	});

	view.act(() => view.find('Pressable').props.onPress?.(Object.create(null)));

	expect(view.text()).toBe('wumpus: 1 star');
	expect(view.find('Text').props.style).toMatchObject({ color: '#FF0000' });
});
```

`render` sets up three things first:

- `settings`: some of your settings. A section can be given in part. The rest keep their defaults.
- `locale`: the language `@unbound-app/i18n` reads.
- `stores`: Flux stores, by name with or without `Store`. `flux.getStore` and `flux.useStore` read them.

`render` draws function components, `memo`, `forwardRef`, context, and class components with `setState`, `getDerivedStateFromProps` and the mount, update and unmount methods.

Elements are not frozen. React freezes them only in development, and on a phone they are not, so code that assigns `element.type` works in a test too.

A component re-renders when its state changes, when a setting it reads with `useSetting` changes, and when a store it reads changes. To change a store during a test, seed it again with `flux.seed` from `@unbound-app/api/testing`. That also tells each `flux.useStore` reading it. Import it under another name, such as `import { flux as fakeFlux }`, in a file that also imports your plugin's `flux`.

An SVG import renders as an `SvgXml` node inside a component named after the file, such as `Svg(star)`. An image import is the same id as `assets.getIdByName` with its asset name, which `fakeAssetId('icon')` also returns.

## The generated settings panel

With a `settings.ts`, `SettingsPanel` from `@unbound-app/settings` draws the generated panel as named nodes, so a test can assert which rows show:

```tsx
import { render } from '@unbound-app/api/testing';
import { SettingsPanel } from '@unbound-app/settings';
import { expect } from 'bun:test';

const view = render(<SettingsPanel />, { settings: { size: 22 } });

expect(view.findAll('NoticeRow')).toHaveLength(1);
expect(view.find('SliderRow').props.value).toBe(22);
```

Each setting is its row, such as `SwitchRow`, `SliderRow` or `ColorRow`, and a `setting.button` is a `ButtonRow` and a `setting.notice` a `NoticeRow`. A `setting.section` is a `Section` with its `title`. Each row has `path`, `title`, `subtitle`, `disabled`, and for a setting `value` and `onChange(value)`. A button has `onPress()`, which runs its action from `src/actions.ts`, and `confirm`, the question the client asks first. A notice has `tone`. The title and subtitle are the plugin's messages in the active locale, and are also the row's text.

The panel follows the client's: a `hidden` setting or section draws nothing, and a row draws only while its `visibleWhen` holds. A row is `disabled` while its `disabledWhen` holds. Predicates run on the live settings, and the panel draws again when one changes.

## Switch the language

`setLocale` changes the language for the rest of the test. Every rendered component that reads your messages draws again.

```tsx
import { render, setLocale } from '@unbound-app/api/testing';
import { expect, test } from 'bun:test';
import { messages } from '@unbound-app/i18n';
import { Text } from 'react-native';

function GreetingTitle() {
	return <Text>{messages.GREETING_TITLE}</Text>;
}

test('shows the title in German', () => {
	const view = render(<GreetingTitle />);

	setLocale('de');
	expect(view.text()).toBe('Willkommen zurück');
});
```

`format` uses the language's real plural rules and number format. In `de`, `{count, plural, one {# Stern} other {# Sterne}}` with `1200` is `1.200 Sterne`. A key the language's file is missing shows en-US, as on a phone.

## Type your options

`render`'s `settings` and `locale`, and `setLocale`, accept anything until you name your plugin's types. Add one file to `tests/`:

```ts tests/unbound-testing.d.ts
import type { Settings } from '@unbound-app/settings';

declare module '@unbound-app/api/testing' {
	interface PluginTypes {
		settings: Settings;
		locale: 'en-US' | 'de';
	}
}
```

Now a setting you don't have, a value of the wrong type, or a language you don't ship is a type error.

<Note>
	The preset finds your plugin from the nearest `manifest.json` above the first test file bun runs. Set `UNBOUND_PLUGIN_ROOT` to point it somewhere else.
</Note>
