Most plugins never need this page. It's for plugins that change Discord's **native** views, such as rounding avatars or recoloring message bubbles, and see a flicker when they do it from JavaScript.

## Why changes from JavaScript flicker

Native views are created, laid out and drawn on the main thread. Your plugin's JavaScript runs on a separate thread. A hook registered from JavaScript hears about a native call only after it has returned, so your change lands a frame or more later. The user sees Discord's view first, then yours: a circle that turns into a rounded square, or a reused row that briefly shows the previous message.

<Flow caption='A change made from JavaScript'>
	<FlowStep title='Discord lays out the view' />
	<FlowStep title='The frame is drawn' detail="Discord's version" />
	<FlowStep title='Your hook runs' detail='On the JavaScript thread' added />
	<FlowStep title='Next frame' detail='Your version' />
</Flow>

**Worklets** fix this. A worklet is a small function that runs on the main thread, inside Reanimated's UI runtime. A hook installed from a worklet runs inline, during Discord's own call. Your change is part of the same layout pass, and is drawn in the same frame.

<Flow caption='The same change made from a worklet'>
	<FlowStep title='Discord lays out the view' />
	<FlowStep title='Your hook runs' detail='Inline, on the main thread' added />
	<FlowStep title='The frame is drawn' detail='Your version' />
</Flow>

<Note>
	Use worklets only for changes that must be in place before the frame is drawn. Keep everything else on the JavaScript thread: Flux stores, settings, network requests, React patches, and anything heavy.
</Note>

## Writing a worklet

A worklet is a function whose body starts with `'worklet'`. `ubd build` compiles every worklet, including those in files you import. Any function a worklet calls must be a worklet too.

```ts src/avatars/ui-avatars.ts
import type { NativeObjCBridge, NativeObjectHandle, NativeUIScope } from '@unbound-app/api/native';

function round(objc: NativeObjCBridge, avatar: NativeObjectHandle, radius: number) {
	'worklet';
	const layer = objc.invoke(avatar, 'layer', []);

	objc.invoke(layer, 'setCornerRadius:', [radius]);
}

export function installAvatarHooks(scope: NativeUIScope, radius: number) {
	'worklet';
	const { objc } = scope;

	if (!objc) return;

	objc.hook('DCDAvatarView', 'layoutSubviews', {
		after: ({ self }) => {
			try {
				round(objc, self, radius);
			} catch (error) {
				console.error(`[Avatar Radius] ${String(error)}`);
			}
		},
	});
}
```

A worklet runs in its own JavaScript runtime. It can't see your plugin's variables, stores or settings. Values reach it as arguments. Constants and other worklets it uses are copied in when it's built, so a variable that changes later is never seen.

## Running worklets

`context.native.ui` runs worklets. The plugin gets `context` as the argument of `start`.

```ts src/avatars/index.ts
import type { PluginContext } from '@unbound-app/api/native';

import { installAvatarHooks } from '~/avatars/ui-avatars';

export function startAvatars(context: PluginContext, radius: number) {
	const { ui } = context.native;
	const scope = ui.createScope();

	ui.run(installAvatarHooks, scope, radius);
}
```

<ParamField path='ui.createScope()' type='NativeUIScope'>
	Opens a scope for the UI runtime. Pass it to a worklet as an argument. It has every synchronous native method your plugin's Capabilities allow: `objc` on iOS, `java` and `hooks` on Android. Methods that wait, such as `invokeAsync`, `batch`, `snapshot` and `findViews`, are left out, because a worklet must never wait on the thread it runs on. Unbound disposes every scope when the plugin stops, which removes its hooks.
</ParamField>
<ParamField path='ui.run(worklet, ...args)' type='void'>
	Queues the worklet on the UI thread. Use it to install hooks, push new data and restore views.
</ParamField>
<ParamField path='ui.call(worklet, ...args)' type='Promise'>
	Runs the worklet and resolves with what it returns, which must be serializable. Use it for self-tests and counts.
</ParamField>

Arguments must be serializable, or a scope. Unbound runs every worklet behind a guard, so an error it throws is logged instead of crashing Discord. Hook callbacks still need their own `try`/`catch`, as in the example above.

## Hooks on each platform

On iOS, `before`, `after` and `replace` callbacks of hooks installed through a scope run inline on the main thread. A `replace` callback that measures a view, such as `sizeThatFits:`, answers without waiting on the JavaScript thread.

On Android, a listener passed to `hooks.hook` through a scope runs inline when the hooked method runs on the main thread. Pass `{ notify: 'after' }` to hear about the call after the original method ran. A hook on a row's bind method then sees the row already bound to its new message.

## Keeping data in the UI runtime

Data your hooks need, such as a server's role colors, comes from the JavaScript thread. Compute it there, and push a plain snapshot into the UI runtime with `ui.run`. Worklets keep it on `globalThis` in the UI runtime, under a key unique to your plugin.

```ts src/avatars/ui-avatars.ts
const RADIUS_KEY = '__avatarRadius';

export function setAvatarRadius(radius: number) {
	'worklet';
	Reflect.set(globalThis, RADIUS_KEY, radius);
}
```

- **Push only when the data changes.** Pushing on every render keeps the JavaScript thread busy while the user scrolls. Compare with the last push, and debounce bursts.
- **Cache what the slow path measures.** Store the result per message in the UI runtime, such as a bubble's frame. The next layout of that message can draw it at once.
- **Clean up on reuse in the same pass.** Remove your own views in `prepareForReuse` on iOS, or in an after-bind hook on Android. Tag those views so the hook finds them without searching.

## What stays on the JavaScript thread

Every native call from a worklet costs about 15 to 35 µs on iOS, and 30 to 50 µs on Android. A hook that runs while the user scrolls can afford a handful of calls, not a walk over hundreds of views. Keep these on the JavaScript thread:

- View-tree snapshots, searches, and anything that measures many views.
- Mounting React surfaces with `fabric`, which renders on the JavaScript thread anyway.
- Flux stores, settings and network requests.

## Worklet rules

- Start every worklet, and every function it calls, with `'worklet'`.
- Wrap hook callbacks in `try`/`catch`. On Android, an error thrown inside a native callback is fatal, and the guard can't catch it.
- Look up Objective-C handles and Java references inside the worklet, instead of passing ones from the JavaScript thread. Android association keys can be passed as arguments.
- Check a Java boolean with `javaFlag`. A boxed `{ type: 'boolean', value: false }` is truthy.
- Don't declare Capabilities for worklets. `ubd build` finds their native calls like any other.
